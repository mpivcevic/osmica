## What this part is, and what it deliberately is not

C3's behavioural change — the PIN moving onto the device — is **not in this
file.** Part 1 builds the recovery path that has to exist before that change is
safe, and makes the state it depends on visible.

Nothing here changes how a waiter logs in. PIN login still works exactly as it
does today, on both projects, after every step below.

**Why the gate exists.** Today a waiter who clears their browser data is
inconvenienced: the session is gone, but PIN login still gets them in. C3e moves
the PIN check onto the device and C4 deletes `login_waiter_by_pin` and
`verify_waiter_pin` outright. After that, a cleared browser means no session, no
local hash and no PIN path — and a fresh invite **cannot bind**, because
`link_waiter_to_auth` requires `auth_user_id IS NULL` (`014:71`) and theirs is
set. Permanent lockout, no self-service path, no owner-facing fix. `017` is that
fix, and its round trip has to be proven before C3e is written.

Part 2 (C3e, C3f, C4) gets its own file, written **after** step 4 below passes.
It is written then rather than now because C3e's shape depends on what the
re-invite after an unlink actually does — whether it lands on `setup` or on
`recover` is the exact bug class v4.39 already existed to fix, and guessing it
in advance is how it reappears.

## Step 1 — read the gate in SQL ⏳

On **both** projects, and never from the admin panel — the panel is exactly what
step 3 fixes:

```sql
select name,
       joined_at    is not null as activated,
       auth_user_id is not null as linked
from public.waiters order by name;
```

Write the answer down here. It is the "before" side of step 4, and it is also
C3's real gate: **every waiter who will still be on staff when C4 runs must read
`linked = true`.** A row with `activated = true, linked = false` is a person who
can open the app, see the roster, and silently fail to raise a swap request.

*(Expected on production as of 22 Aug: seven rows, Mara linked, the rest not —
the rest being placeholders rather than real staff.)*

## Step 2 — apply `017` on dev ⏳

SQL editor on **osmica-dev** (`simavghwjnqytcyeunto`), paste the whole file. It
is one transaction: it either all lands or none of it does.

🔴 **Paste the file, do not re-run a saved query.** Trap 3: a saved query
re-applies its own older text and still reports success.

Then verify what actually landed rather than the green box — the `VERIFY` block
at the bottom of `017` has the four checks. The two that matter most:

```sql
select proname, proconfig, prosecdef from pg_proc
where proname in ('owner_unlink_waiter','owner_list_waiters');
-- expect: prosecdef true for both,
--         proconfig {search_path=public, extensions, pg_temp} for both
```

Then the check the SQL editor cannot do for you. The query above ran as a
superuser, so it proves the function is *shaped* right and says nothing about
who can **call** it. This asks the only question that matters for a stranger:
holding nothing but the publishable key that ships in the page source, and no
login, can I reach `owner_unlink_waiter`?

Paste it into a terminal — or type `!` and paste it into the Claude session to
run it there. Read-only: the uuid names a waiter that does not exist, so it
cannot change anything even if the answer is bad.

```bash
curl -i -X POST 'https://simavghwjnqytcyeunto.supabase.co/rest/v1/rpc/owner_unlink_waiter' \
  -H 'apikey: sb_publishable_xOx4POsl9coB1utDMHlHAw_h1q4oxWA' \
  -H 'Content-Type: application/json' \
  -d '{"p_waiter_id":"00000000-0000-0000-0000-000000000000"}'
```

That is dev's key, from `osmica.html:1118`. It is public by design — sending it
is the whole point, because it is exactly what a stranger holds.

**✅ Pass** — the first line reads `HTTP/2 404` or `HTTP/2 401`, and the body is
one of:

```json
{"code":"PGRST202","message":"Could not find the function public.owner_unlink_waiter(p_waiter_id) in the schema cache"}
{"code":"42501","message":"permission denied for function owner_unlink_waiter"}
```

Either means `anon` holds no `EXECUTE`, and PostgREST will not even admit the
function exists.

🔴 **❌ Fail — and this is the one that reads like a pass.** A body carrying
`not_owner`:

```json
{"code":"P0001","message":"not_owner"}
```

`not_owner` is raised from *inside* the function body. Seeing it means the caller
got through the grant, entered the function, and was stopped only by the
ownership check — the second line of defence doing the first one's job. The grant
is what has to stop a stranger at the door.

**❌ Also a fail:** any `200`, especially with a uuid-looking string in the body.
That is a rotated invite token, and it would mean the probe just unbound a real
waiter.

On any fail, stop — do not go to step 3. Re-run `017`'s closing
`REVOKE EXECUTE ... FROM anon, PUBLIC` lines and probe again.

> `017` drops and recreates `owner_list_waiters` — a `RETURNS TABLE` signature
> cannot be changed by `CREATE OR REPLACE`. It is inside the transaction, so
> there is no window where the function is missing. **A v4.39 client keeps
> working against the new signature**: the extra `linked` field arrives in the
> JSON and is ignored. That is why `017` can go to production before v4.40 does,
> and step 6 uses that order deliberately.

## Step 4 — 🔴 the unlink round trip on dev ⏳

**This is the step C3 is gated on.** C4 deletes the last fallback, so if this is
broken when C4 runs it is broken permanently, and one cleared browser costs a
staff member their access for good.

Use a waiter who already reads `linked = true` on dev — Eva or Ana.

1. **Unlink.** Admin panel → 🔓 → confirm. A new invite link appears
   immediately. Copy it.
2. **Confirm the release landed:**
   ```sql
   select name, joined_at is not null as activated,
          auth_user_id is not null as linked
   from public.waiters where name like 'Eva%';
   -- expect: activated = false, linked = false
   ```
   `joined_at` going false is deliberate, not a bug: it is what sends the next
   invite down the `setup` branch, the only branch that can establish a **new**
   PIN. After C3e the old PIN exists only on the device that is gone.
3. **Confirm the old link is dead.** Open the *previous* invite URL — the one
   from before the unlink. It must refuse. `017` rotates the token, so a
   forwarded copy is inert.
4. **Claim it on a clean profile.** New private window — not the one that holds
   the old anonymous session, or you are testing `linked_elsewhere` instead.
   Open the new link, set a new PIN.
5. **Confirm the rebind:** the same SQL now reads `activated = true,
   linked = true`.
6. **Confirm they can write.** As that waiter, raise a swap request. It must
   succeed. A refusal here means the row rebound to the wrong identity.

If any of 1–6 fails, **Part 2 does not get written.** Report which one and what
it did instead.

## Step 5 — the C3c / C3d checks on dev ⏳

These are the "say why" changes. Both are about a screen that used to stay
silent, so the check is that words appear — not that something works.

🔴 **Prove which session the browser holds before every check below.** The
displayed identity and the session can disagree — the app can show Ana while the
database sees Eva — and nothing on screen distinguishes them. Devtools console,
on the tab you are about to test:

```js
(await sb.auth.getUser()).data.user ?? 'no session'
```

- `is_anonymous: true` → a waiter device. Match the `id` against `auth_user_id`
  in SQL to know **which** waiter.
- `is_anonymous: false` → the owner. Wrong window for any waiter check:
  `linkWaiterIdentity` returns `owner_session` and skips linking entirely, by
  design, so no message appears and the result means nothing.
- `'no session'` → role `anon`, never linked.

> The first run of step 5 on 22 Aug produced two false passes because an owner
> login had happened in the incognito window and nothing recorded it. Keep the
> console open throughout: every v4.40 failure path logs a `[Osmica]` warning,
> which is the second witness when a 7-second toast is missed.

**Contexts.** All incognito windows share one session, and it dies only when the
last one closes — so the linked-waiter device and the no-session browser cannot
both be incognito at once. Use **incognito** for the linked device, and a
**Chrome Guest window** for the no-session checks. Never sign in as the owner in
either, and keep the DEV switcher out of the incognito one.

**5a — a link that resolves but cannot bind says so.** In the Guest window
(`'no session'`), open the **current** invite link of a waiter who is already
linked to another device, and enter their PIN. The PIN is accepted and you land
in the app; expect *"Ova poveznica više ne vrijedi. Zatraži novu od vlasnika."*
and `[Osmica] link_waiter_to_auth returned: invalid_token` in the console. Then
confirm in SQL that the waiter is **still** bound to their original uid — the
refusal has to protect the binding, not overwrite it.

> ⚠️ **Not "change the last character of the token".** A mangled token never
> survives `claim_invite`, so it stops at the pre-existing invalid-link screen
> (`osmica.html:694`, *"Link nije valjan"*) and never reaches the code C3c
> changed. The case that matters is trap 13: the token is real, the waiter row
> is already bound, and `link_waiter_to_auth` returns `invalid_token` rather
> than `already_linked` because it is the *caller's* uid that is unbound. Before
> v4.40 that failed with nothing but a console warning.

**5b — a second claim in one browser is caught.** In the incognito window from
step 4, open the invite link of **a different waiter from the one step 4 used**,
and complete the PIN. Expect *"Ovaj je preglednik već povezan s drugim članom
tima…"* and `[Osmica] This browser is bound to a different waiter: <id>`.

Then confirm in SQL that **neither** row moved: the step 4 waiter still holds the
window's uid, and the second waiter is unchanged.

> ⚠️ **It must be a different waiter.** Re-opening the link of the waiter this
> browser is already bound to is the benign case, and v4.40 correctly says
> nothing: `already_linked` with the uid on the expected row is success.
>
> You will still land in the app afterwards — linking is non-fatal by design, so
> a failure degrades to read-only rather than locking anybody out. The state that
> leaves is worth understanding: the app shows the second waiter, the database
> sees the first, and every write is refused because `sr_waiter_insert` checks
> `waiter_id = current_waiter_id()`. Safe, and ugly. Whether C3e should refuse
> to enter the app at all on `linked_elsewhere` is a Part 2 decision.

> This is the Ana Anić failure from 22 Aug. `link_waiter_to_auth` returns
> `already_linked` when the **caller's** uid is bound *anywhere* (`014:57-63`),
> and v4.39 counted that as success — so the waiter the invite named stayed
> unlinked and nothing on screen said so. v4.40 checks whose row holds the uid
> before believing it (trap 13).

**5c — a refused write says what to do.** Take a waiter who reads
`linked = false`, open the app as them, raise a swap request. Expect
*"Ovaj uređaj nije povezan s tvojim računom…"* — **not** *"Greška. Pokušaj
ponovo."*

**5d — a refused *cover* also says it.** Same waiter, offer to cover an open
request.

> ⚠️ **Scope note — this went slightly past C3d, on purpose.** `coverRequest`
> and `handleApproval` sent their `UPDATE` with no `.select()`. Trap 8: an update
> whose row the policy filters away returns 204 with **no error**, so the client
> saw success and rendered a swap the database never recorded. A "specific error
> message" would simply never have fired on those two paths. v4.40 adds
> `.select('id')` to both and treats an empty result as a refusal.

**5e — the owner is unaffected.** Sign in as the owner, approve and reject a
request. Both still work, and neither shows a refusal message.

**5f — the silent refusal is caught.** 5c and 5d exercise the *grant* layer:
with no session the caller is `anon`, PostgREST answers `401` with
`42501 permission denied for table shift_requests`, and the message comes from
the error branch. The branch `.select('id')` was added for is the other one — an
authenticated caller whose row the policy filters away, which returns **204 with
no error at all**.

To reach it, use the Guest window straight after 5a: `signInAnonymously()` ran
there and left an anonymous session bound to no waiter row. Confirm with the
one-liner that it now reads `is_anonymous: true` rather than `'no session'`, then
offer to cover an open request belonging to somebody else (`!isMine` at
`osmica.html:2675` is what renders the button).

- **Expect:** `204` in the network tab, the toast appearing, and **no**
  `[Osmica] write refused` line — that line only prints from `writeErrorMessage`,
  so its absence is what proves the empty-result guard fired.
- 🔴 Nothing on screen means `.select('id')` is not doing its job and the silent
  success is still live.

**5g — the policy layer refuses an insert.** Same context, raise a swap request.
Expect `403` and `42501 new row violates row-level security policy`, with the
same toast. Same message as 5c, different mechanism — trap 12, and worth seeing
both at least once so the codes are familiar when something really breaks.
