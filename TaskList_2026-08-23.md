## What this part is

Part 1 built the way back — the owner can release a device and reissue an
invite, and the panel shows who actually holds one. Part 2 spends that safety
net: the PIN stops being a question the database answers, and then the functions
that used to answer it are deleted.

**After C3e (v4.42), a waiter's PIN never leaves their phone.** It is compared
against a PBKDF2 hash in `localStorage`. Identity comes from the anonymous
Supabase session bound to their row by `014`, not from four digits.

**After C4 (`018`), `login_waiter_by_pin` and `verify_waiter_pin` do not
exist.** With them goes the shape that Stage A could only ever make expensive:
a café id and four digits, sent by anyone holding the publishable key, answered
with *which member of staff you just became*.

### Two decisions taken while writing this, both departures from the plan

**1. A linked waiter still types their PIN on every cold open.**
`osmica_stage_c_plan.md`'s C3f check 2 says a waiter with a live session should
land in the app "with no PIN prompt at all", and its check 1 says a waiter
unlocks with their PIN — those cannot both be true. Resolved in favour of the
keypad: the session decides *who you are*, the PIN decides *whether the app
opens on this phone right now*. Nothing about the waiter's day changes, and the
PIN keeps the one job the plan claims for it — a colleague picking up an
unlocked phone. C3f check 2 below is rewritten accordingly.

**2. The invite screen's `setup` / `recover` branches are collapsed.**
They used to be chosen by `waiter.joined_at`; v4.42 chooses by whether *this
browser* already holds a local hash for that person. This is the direct answer
to part 1's finding that the re-invite after an unlink always lands on `setup`,
so `recover` was never exercised by the route that needs it. Rather than write
the local hash into both branches and hope the second one is tested, v4.42
removes the asymmetry: one path, one link call, one place a PIN is written.

Asking a returning waiter for their old PIN proved nothing anyway. The invite
token is the credential in both branches, and `link_waiter_to_auth` refuses any
row that is already bound (`014:71`) — so a link that reaches a claimable row is
a link the owner issued for that row. After C3e the old PIN exists only as a
hash on a device the waiter no longer has, which is usually why they are
standing there.

### The order is not interchangeable, and here is why

`017` could go to production before v4.40 did, because a v4.39 client kept
working against the new signature. **`018` has no such property.** A v4.41
client calls `set_waiter_pin_by_token` when an invite is completed and
`verify_waiter_pin` on every login; drop those with v4.41 still being served and
the app stops working for everyone at once.

So: **v4.42 everywhere first, `018` second, per project.** v4.42 against an
untouched database is safe in the other direction — it simply stops calling
three functions that still exist.

High-water mark becomes `018`. The next file, either project, is `019`.

## Step 2 — v4.42 on the tunnel ⏳

`main` carries v4.42. Point the tunnel at it and confirm the marker reads
**v4.42** and the DEV pill is green.

### What changed, so you know what you are looking at

- The PIN is checked by `verifyLocalPin()` against `localStorage` — key
  `zm_b_pin_<waiter id>`, PBKDF2-HMAC-SHA256, 210,000 iterations, 16-byte salt.
- `init()` resolves a waiter from `auth.uid()` and shows *their* keypad. The
  waiter session in `localStorage` is display data now; the JWT is the identity.
- **The PIN-only screen is gone.** No session on this device means no way in
  except an invite link.
- **The login keypad has a third mode.** A waiter with a session and no local
  hash is asked to *set* one, twice. This is not an edge case: it is what every
  waiter linked before v4.42 sees on their first open — Mara on production, Eva,
  Ana and Bruno on dev.
- **A failed link is now fatal.** No identity, no PIN stored, no entry, and the
  screen says which of the five failures it was. `owner_session` joined that
  list: it means linking was skipped because the owner was signed in here, which
  is precisely the 22 Aug false pass.
- The DEV panel gained a fourth line: whether this device holds a local PIN.

### First look

Open the tunnel URL on a phone or in a private window that already holds a
linked waiter's session. Expect: their name, the keypad, and the instruction
**"Postavi 4-znamenkasti PIN za ovaj uređaj."** — not a request for the old one.

🔴 **Prove the session before believing anything on this screen.** Open the DEV
panel and read all four lines. `session: anonymous`, a uid, a name, and the
local-PIN line. If it says `session: OWNER`, you are in the wrong window and
every check below will pass for the wrong reason.

## Step 3 — the C3f checks on dev ⏳

Nine checks. 1–5 are `osmica_stage_c_plan.md`'s C3f, with check 2 rewritten per
the decision above; 6–9 are new and exist because v4.42 changed things C3f was
written before.

Run them in order. Each says what a pass looks like *and* what the failure that
resembles a pass looks like, because that distinction is the entire lesson of
22 Aug.

🔴 **Before every check that involves a waiter, read the DEV panel.** Session
kind, uid, which waiter holds it, and whether a local PIN exists. Two of part
1's checks passed for the wrong reason for want of that, and nothing on screen
recorded it.

### 3.1 — the network is never asked for a PIN

Log in as a linked waiter with a local PIN set. DevTools → Network, filter
`rpc/`, then enter the PIN.

- ✅ **Pass:** no request at all while the four digits are entered. The requests
  that follow are `cafes`, `waiters`, `shift_requests` — the app loading.
- ❌ **Fail:** any `rpc/verify_waiter_pin` or `rpc/login_waiter_by_pin`. That
  means a v4.41 tab, or a call path that survived. Reload and check the marker.

### 3.2 — a live session skips café and PIN *resolution*, not the keypad

Close the app fully and reopen it as a linked waiter.

- ✅ **Pass:** their own name above the keypad, with no café chooser and no
  "which waiter is this" round trip. The name came from `auth.uid()`.
- ❌ **Fail:** the generic keypad with no name, or "Nisi još aktiviran/a". Both
  mean `resolveWaiterBySession()` found nothing — check the DEV panel's uid
  against `auth_user_id` in SQL.

> This is the rewritten check. The plan said "no PIN prompt at all"; the keypad
> is deliberate. See the decisions at the top of this file.

### 3.3 — offline unlock

Airplane mode, or DevTools → Network → Offline. Reopen the app and enter the
PIN.

- ✅ **Pass:** the keypad accepts it and the app moves past the login screen.
  It will then fail to load the roster — there is no offline cache for API data,
  and that is expected and not part of this check.
- ❌ **Fail:** the keypad rejects a correct PIN, or the screen says the device is
  no longer linked. The second one is the dangerous failure: a dropped packet
  must never release a binding, and `init()` distinguishes "could not ask" from
  "asked, answered nobody" precisely to prevent it.

### 3.4 — no new `pin_hash` is written

After a waiter sets a PIN under v4.42:

```sql
select name, pin_hash is not null as has_server_hash,
       joined_at is not null as activated,
       auth_user_id is not null as linked
from public.waiters order by name;
```

- ✅ **Pass:** the row you just set a PIN on reads `has_server_hash = false`,
  `linked = true`. Older rows may still carry a hash from before v4.42 — that is
  history, and `018` deletes the column.
- ❌ **Fail:** `has_server_hash = true` on the row you just touched.
  `set_waiter_pin_by_token` is still being called from somewhere.

### 3.5 — 🔴 the recovery round trip (this is C4's gate)

The one C4 is irreversible without. Use a linked dev waiter — Eva or Ana.

1. Admin panel → 🔓 → confirm. Copy the new link.
2. `select name, joined_at is not null as activated, auth_user_id is not null as linked from public.waiters where name like 'Eva%';` → both false.
3. Open the **old** link. It must refuse — `017` rotated the token.
4. Open the new link in a **different browser** (not another incognito window in
   the same one: they share a session, so you would be testing
   `linked_elsewhere` instead). Set a new PIN.
5. Same SQL: both true again.
6. As that waiter, raise a swap request. It must succeed.

- ✅ **Pass:** all six, with the uid in the DEV panel matching `auth_user_id`.
- ❌ **Fail at 6 with a refusal message:** the row rebound to the wrong identity.
  Compare the uid before and after; they must differ.
- ❌ **Fail at 4 with "Ova poveznica više ne vrijedi":** the row was still bound.
  Check that step 1 actually cleared `auth_user_id`.

**If this fails, steps 6 and 7 do not run.** Everything else in this file can be
retried; `018` cannot.

### 3.6 — the same-device unlock path (what used to be `recover`)

Still as the waiter from 3.5, in the browser that just claimed the invite: open
the **new** invite link again (the one `link_waiter_to_auth` rotated to — read
it from the admin panel's 💬/copy button).

- ✅ **Pass:** "Upiši PIN za prijavu na ovom uređaju." — one entry, not two. It
  accepts the PIN set in 3.5 and lands in the app.
- ❌ **Fail:** it asks you to *set* a PIN twice. The local hash was not found —
  check `localStorage` for `zm_b_pin_<waiter id>`.

This is the branch that part 1 warned would never be exercised by the recovery
route. Under v4.42 it is reachable deliberately, and this check is how.

### 3.7 — an unlinked device tells the truth

With a waiter logged in on one device, unlink them from the admin panel on
another. Then reload the waiter's device.

- ✅ **Pass:** "Ovaj uređaj više nije povezan s tvojim računom. Zatraži novu
  poveznicu od vlasnika." — and the DEV panel now reads `session: none`, because
  `init()` signed the dead session out.
- ❌ **Fail — and it reads like a pass:** the app opens normally and only fails
  later when they try to write. That is the state C3d was built to name, and
  here it means the session was left in place. Re-check that the DEV panel says
  `none` and not `anonymous`.

Leaving that session alive is not cosmetic: the next invite claimed in this
browser would return `already_linked` and bind nobody, which is trap 14 and how
Ana Anić stayed unlinked on 22 Aug.

### 3.8 — the owner-session guard bites

In a window where the **owner is signed in**, open a waiter invite link and set
a PIN.

- ✅ **Pass:** "Na ovom je pregledniku prijavljen vlasnik. Odjavi se ili otvori
  poveznicu u privatnom (incognito) prozoru." and you do **not** enter the app.
- ❌ **Fail:** you land in the app as that waiter. Then the owner's JWT is what
  authorises every write you make, which is exactly the false pass that made two
  of part 1's step 5 checks meaningless.

### 3.9 — the unlinked waiters cannot get in at all

Use Cvita, Duje or Marko — `activated = true, linked = false` on dev.

- ✅ **Pass:** there is no way to reach the app as them. No PIN-only screen
  exists any more, and an invite link for their row is the only entry.
- ❌ **Fail:** any keypad accepts four digits and lets you in as them. That means
  a v4.41 tab.

This is what the C4 gate is protecting real people from. It is meant to be
uncomfortable to watch.

4. Run `018`'s four VERIFY queries. The one that matters most is the probe from
   outside, because the SQL editor answers as a superuser:

   ```bash
   curl -i -X POST 'https://simavghwjnqytcyeunto.supabase.co/rest/v1/rpc/login_waiter_by_pin' \
     -H 'apikey: sb_publishable_xOx4POsl9coB1utDMHlHAw_h1q4oxWA' \
     -H 'Content-Type: application/json' \
     -d '{"p_cafe_id":"00000000-0000-0000-0000-000000000000","p_pin":"1234"}'
   ```

   That is dev's key, from `osmica.html`. It is public by design — sending it is
   the point, because it is exactly what a stranger holds. The uuid names no
   café, so the call cannot do anything even if the answer is bad.

   - ✅ **Pass:** `404` and `PGRST202`, "Could not find the function
     public.login_waiter_by_pin … in the schema cache".
   - ❌ **Fail:** `401` with `42501`, "permission denied for function". The
     function is still there and only a grant is stopping the caller. This step
     is about it not existing.
   - ❌ **Fail:** any `200`.

5. **Then press 🔓 in the admin panel on a linked waiter.** This is not
   optional. `018` rewrites `owner_unlink_waiter` to stop assigning `pin_hash`,
   and Postgres does not check function bodies when a column is dropped — so
   getting this wrong produces a function that is fine in `pg_proc`, fine in
   every query you can write, and throws "column pin_hash does not exist" the
   first time an owner actually uses it. The SQL editor cannot catch it. The
   button can.

## What this leaves for Stage D

Anonymous reads of names, colours, shift patterns and schedules — the last open
item, and the one every stage since A has been clearing the way for. It was
blocked on C4 because a waiter with no session had to be able to render the café
and the roster before authenticating. After this file, nobody authenticates
without a session, so `waiters_read`, `cafes_read`, `sr_read` and `ds_read` can
finally stop saying `USING (true)`.
